# 当前版本 Release：有则检查，缺则补齐

本流程承接主技能的备份、clean version、README 修复和六类清理，发布对象必须是最终验证过的干净提交。用户已要求将它作为推送项目时的默认后续流程；有明确的只审查、只准备或不发布限制时遵从限制。更新技能本身不是立即发布项目的指令。

## 1. 确定当前版本与发布条件

- 优先使用用户明确指定且与项目事实一致的当前版本，再根据项目的权威版本来源确定：例如 `package.json`、`pyproject.toml`、`Cargo.toml`、项目版本文件或实际版本生成机制。结合发布配置、已有 tag 和变更记录交叉核对。不要把依赖版本、模板示例版本或远端最新版本当成本项目当前版本。
- 区分版本号与 tag 命名。沿用本项目约定，例如版本 `1.2.3` 对应 `v1.2.3`；同版本已有 tag 时复用现有拼写，不再生成另一套前缀。多个独立组件的版本不要求强行一致，确定本次发布对象；缺少版本或无法裁决的冲突时保留其他准备成果，只询问必要的版本/组件信息，不擅自写入 `0.1.0`、`1.0.0` 或提升版本。
- 判断依据是：README 六项检查合格（原有五项内容加中英双语，且两种语言完整一致）、六类清理及历史检查完成、发布内容已提交、相关构建/核心测试或最小用例通过、项目约定的必需发布检查满足、版本与代码/发布记录一致。复用先前针对同一最终提交的有效验证；没有测试框架的项目使用合适的最小验证，不为发版强造一套测试。
- 查看现有发版流程和 CI：若推送 tag 会自动构建或创建 Release，优先沿用并核验结果，避免与自动化争抢发布。不要为了方便关掉检查、绕过受保护分支或另建一套发布流水线。依赖 Git tag 生成版本的项目，先按其既定机制验证版本解析，再完成需要真实 tag 的检查。
- 预发布版本（如项目约定的 alpha、beta、rc、dev）保留原版本并正确标为 prerelease，不能通过删后缀冒充正式版。不把“全部测试未能运行”写成通过；实际影响发布的未验证项或失败先处理。该功能不意味着有权另外发布 npm/PyPI 包、部署服务或改变仓库可见性。

## 2. 准备四项发布内容

在推送新 tag 和发布之前完成并核对以下内容。正文先保存为仓库外的 UTF-8 文件，避免 shell 转义破坏换行或将私人检查报告带入发布包。

| 项目 | 规则 |
| --- | --- |
| 对应版本号的 tag | 使用已核实的版本及项目命名约定；最终解析到经过验证的完整提交 SHA，不能指向清理前的代码或漂移的默认分支。 |
| Release 标题 | 默认使用“项目名 + tag”，已有准确标题则保留；版本与 tag 一致，避免夸大。 |
| 简洁的发布说明 | 一小段概述加必要的变更要点。基于该 tag 的实现和可核实的变更记录；首次发布说明这是首次发布，不杜撰与不存在旧版本的差异。保留已有准确且有用的内容。 |
| 当前功能 | 在 Release 正文单列“当前功能”，简要列出该版本已实现的主要能力，与 README 及代码一致；不能把后续提交、计划功能或未验证能力写成该版本现有功能。 |

安装/使用链接以及已知限制有必要时简短补充，避免复制整份 README、原始提交日志或冗长扫描记录。发布语言沿用项目约定，无约定时中文。标题、正文、tag 注释与附件均执行敏感信息复查。默认不额外上传原目录压缩包、备份、日志或未经审核的构建产物；既定发布流程需要附件时从干净提交构建并复核。

## 3. 检查已有状态并保持重复执行安全

明确 GitHub 主机、仓库、目标分支/提交及可用的登录权限。通过可用连接器或 GitHub CLI/API，读取远端 tag（带注释 tag 要解析到提交）、对应 Release、草稿和仓库发布规则，同时检查隔离发布工作区中的本地 tag。不要把权限错误、网络失败或无法读取的草稿当作“没有 Release”。

| 状态 | 操作 |
| --- | --- |
| 本地和远端都没有该 tag | 在最终干净提交创建带注释的 tag，遵循项目签名要求，再仅推送这个 tag。 |
| 仅本地有正确 tag | 核对注释、提交和版本后推送；本地 tag 指向不符时停止该 tag 的发布，不使用强制替换。 |
| 远端已有正确 tag，没有 Release | 复用远端 tag，补齐发布内容并创建 Release；不重复创建 tag。 |
| 远端 tag 正确，已有草稿 | 保留准确内容及已审核附件，补齐四项、通过检查后发布；用户明确要求保留草稿时不发布。 |
| 已发布且四项完整正确 | 验证提交、版本和发布状态后直接返回现有链接，不制造重复提交、tag、Release 或重复追加功能段落。 |
| 已发布但标题、说明或当前功能缺失/错误 | 先把原有远端发布元数据保存到私人备份，再仅补齐或纠正这些可编辑字段；按原 tag 的代码写内容，保留附件和正确设置。 |
| 同版本 tag 指向其他提交，或 Release 与当前发布对象冲突 | 不移动/删除已有 tag，不强推、不删 Release 重建、不悄悄加版本后缀。给出已存在的提交与待发布提交以及需选择的新版本/目标问题，暂停该版本发版。 |

先比较发布内容；clean version 没有实际变化时，不为了重复运行而生成新提交，从而人为制造同版本冲突。检查本地和远端各自状态；二者不一致时不能只取其中一个放行。即使最终文件看似相同，也不能将明确不同的发布提交悄悄冒充同一 tag 的原始目标。

遵守仓库不可变发布和签名规则；不得降低保护设置来修改 tag 或附件。不可变 Release 的标题和说明仍可按 GitHub 支持的方式更新，不能据此认定 tag 或附件也可替换。缺失的必需附件若已无法补齐，报告具体限制，不删发布重建来绕过规则。[GitHub 发布管理说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

## 4. 按顺序推送并发布

1. 将所有 README/清理改动纳入干净提交，记录完整 SHA 和四项已准备内容。先完成所有可在本地执行的检查。若需要分支推送，确认最终提交成功到达已授权的目标分支；遵从既定 tag 发布流程所允许的目标，不擅自合并 PR 或改换默认分支。
2. 在隔离发布工作区创建缺失的 tag，显式绑定记录的 SHA；tag 内容审查完毕后，只推送对应 `refs/tags/TAG` 到已确认的远端，禁止使用 `--tags`、`--mirror` 或强制更新顺带上传无关 refs。回读远端并解析 tag，核对其指向该 SHA；受保护 tag 的拒绝不能绕过。
3. 若仓库自动化负责 Release，等待必需检查和自动化结果，再重新读取同 tag 的 Release 并按上表补齐；若自行创建，也要先再次检查是否已被其他进程创建。CLI 示例仅示意参数，实际参数须按当前 shell 引用：

   ```text
   gh release create TAG --repo OWNER/REPO --verify-tag --title TITLE --notes-file NOTES_FILE
   ```

   `--verify-tag` 要求远端 tag 已存在，防止工具在默认分支上自动创建错误的 tag；还需自行核对它的提交。预发布加入 `--prerelease`。旧版本补发不应取代新版本的 Latest，按版本顺序和项目约定设置，必要时使用 `--latest=false`。[GitHub CLI 创建 Release](https://cli.github.com/manual/gh_release_create)
4. 已有 Release 使用更新接口或 `gh release edit`，只变更需修复的字段。已有草稿发布时可使用 `--draft=false --verify-tag`；发布前复核版本、附件、必要检查与目标提交。需要在不可变发布前装配附件时，可以先建草稿再完成发布，但草稿不是最终完成状态。[GitHub CLI 编辑 Release](https://cli.github.com/manual/gh_release_edit)
5. 最后从 GitHub 重新读取 Release 和 tag：核对仓库、版本、提交、标题、简洁说明、“当前功能”、prerelease 状态和已发布状态，返回实际 Release 链接。不能仅凭命令退出码或本地成功就宣称全部完成。

网络错误、权限失败或并发创建时，先回读远端确定实际成功的步骤，再从尚未完成的位置恢复，不盲目重复写入。tag 已成功但 Release 未发布时保留正确的 tag，明确报告部分完成，不自行删除回滚。确认是登录权限或同版本冲突等无法自主解决的问题后，保留备份、clean version 和已准备的正文，简短说明需要用户处理什么；不要无限重试。仅 Release 阶段不满足条件时可以继续独立、已授权且通过检查的代码推送，不将“代码已推送”写成“Release 已发布”。
